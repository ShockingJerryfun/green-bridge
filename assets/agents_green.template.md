# Green Bridge 协作约定

本块只适用于蓝绿协作任务。角色由用户/启动指令确定：蓝区负责代码、派单与判读，绿区负责目标环境执行和证据回传。不要把使用同一仓库的所有代理都认作绿区；`Current owner` 只表示下一位处理者。普通仓库工作遵循其原有约定。用户的最新明确指令优先于此工作流约定。

## 绿区执行任务时

1. 读取 `pingpong.md` 的 Protocol、目标与 `Current round` 指向的轮次，核对目标仓库、分支和代码基线。旧文档没有指针时只接受唯一未完成派单；无法确定时报告歧义，不按标题位置猜测。已交付的同一轮不重复执行，除非收到重跑派单。
2. 先检查本地改动，保留与任务无关的用户工作；同步仅用 `git pull --ff-only`，不 force-push。分叉时保留现场并报告，不强推交付。
3. 完成前置核验后按派单命令执行；参数、测量方法、验收标准保持约定。前置失败或命令异常时停止依赖该步骤的操作并回传。绿区不自行修代码；有指定补丁时先对指定基线运行 `git apply --check`，通过后再应用。
4. 写入本轮交付：代码/派单提交、机器与设备、容器或宿主、时间、前置实际值、执行偏差、退出码、逐项验收证据、原始输出和异常。大日志保存在任务指定的结果文件中，正文提供路径和必要日志行；完整数据不能被摘要替代。未提交或蓝区不可访问的文件明确注明。
5. 在 `history.md` 追加本轮交付事件，更新当前轮次状态及下一位处理者。只暂存 `pingpong.md`、`history.md` 与派单允许的文件；检查暂存差异后提交。派单已授权回传时继续 push 到指定远端/分支，核对远端提交后报告 commit 与状态。回传失败时保留本地提交并报告原因。

绿区可以逐项报告验收是否命中及事实观察，跨轮判读和下一步决策由蓝区完成。环境争用、数据缺失、失败样本如实保留。只完成任务书要求的检查，不自行扩大实验或反复测试。
